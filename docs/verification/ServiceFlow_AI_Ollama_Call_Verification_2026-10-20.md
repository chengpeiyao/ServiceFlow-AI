## 实际调用

使用已交付 JAR 内的 `ModelClient`、同一 `Corpus`、Schema、检索器和校验器，额外探针仅负责编排开发案例 `D-01`，没有替换 HTTP 客户端或伪造响应。当前 JAR 含此前经过 54 项测试的本机 HTTP 适配，Git 工作区该改动尚未提交，不能仅靠 HEAD 提交重现；记录中同时保存 JAR 和资料哈希。

客户原文：`今天09:15全部用户提交订单失败，提示连接池耗尽。` 客户显式字段为 `COMS`、`1.2`。这些产品字段不在该原文字符串中。

参数：`http://127.0.0.1:11434/v1/chat/completions`、`max_tokens=1024`、`response_format=json_schema`、`temperature=0`、请求超时 20 秒。两组顺序执行，并非正式实验的并发 2；没有单独预热。冷启动、顺序及缓存因素未控制，不能用两次延迟比较 A1/A2 的性能优劣。

## 发现的问题

1. 两组都把显式产品字段 `COMS`、`1.2` 作为 `sourceQuote`。值本身不是凭空编造，但不在客户原文中，违反当前原文引文契约，各触发两次 `FACT_QUOTE_MISMATCH`。后续应明确区分原文与显式字段的来源，不能为了通过而放松成任意字符串引用。
2. A1 两次使用 `symptom` 字段，触发 `DUPLICATE_FACT_FIELD`。它还追问了原文已明确的“全部用户”影响范围，说明结构约束与必要追问约束仍需改进。
3. A2 把“连接池耗尽”放入 `change`，属于字段语义错误；原文仅描述症状，没有报告发生前的变更。逐字引用检查无法发现这类错误，仍需语义评审。
4. A2 的引用标识、版本、片段与前置条件通过当前机械检查；这不证明每条建议均有充分证据支持，更不能据一个案例判断 RAG 已有收益。

本轮没有修改提示词、Schema、规则、案例或标注来迎合输出，也没有接入业务写入。完整 20 条开发集、40 条固定检查集、人工评分及 A0/A1/A2 质量比较均未执行。
